## The notebook problem

During my undergraduate years I worked with a wholesale jaggery store in Kolhapur, Maharashtra. The owner had years of daily sales records (dates, item weights, amounts in rupees) stored in a notebook. Everything was there. Ask him why March underperformed and the notebook had no answer. Ask whether to place a large order before the festival season and it just sat there.

We built the first version of B.I.A.S.E.D. for exactly this situation: an Android application backed by an LSTM neural network that could store records, visualize trends, and predict future sales. We tested it on that store's actual data: 61 daily entries from March 2012 to April 2013, split 40 for training and 21 for testing. The model improved with every new entry. Real business, real rupees, real predictions. Not a demo.

But it could predict. It could not explain. Ask "why did March drop?" and it had nothing to say. That limitation turned out to matter more than anything else.

Four years later, with a completely different set of tools available, I rebuilt it from scratch.

## The first version: LSTM and what it taught us

The original application used [Long Short-Term Memory (LSTM) networks](https://www.bioinf.jku.at/publications/older/2604.pdf), a type of recurrent neural network designed specifically for time-series data, proposed by Hochreiter and Schmidhuber in 1997. Unlike standard feed-forward networks, LSTM cells maintain an internal memory state controlled by three gates: an input gate that decides what new information to store, a forget gate that decides what to discard, and an output gate that decides what to pass forward. This gating mechanism lets the network learn patterns across long time spans without the vanishing gradient problem that makes ordinary RNNs impractical on real sequences.

For a business with daily sales records, this is a natural fit. The model treats each day's sales figure as a time step and learns to predict the next value from the history of previous values.

```python
# Keras LSTM setup used in the original version
model = Sequential()
model.add(LSTM(4, input_shape=(1, look_back)))
model.add(Dense(1))
model.compile(loss='mean_squared_error', optimizer='adam')
model.fit(trainX, trainY, epochs=100, batch_size=1, verbose=2)
```

On the jaggery store dataset, accuracy improved consistently as more entries were added, which is exactly the right behavior for a tool meant to grow with a business. The application also had multi-user workspaces, customizable tags per business type, and CSV-based record import. It was deployed with local vendors and used in production.

What it could not do: answer a question. LSTM produces a number, a predicted sales figure for next week. It cannot tell you why last week was low. It cannot reason about your specific business context. It cannot connect a sales dip to a local holiday, a supplier delay, or a price change you made three months ago. It predicts. It does not understand.

That distinction between predicting and understanding is the core problem that the rebuilt version addresses.

## What changed between 2021 and 2025

Two developments made B.I.A.S.E.D.'s current architecture possible.

**Large language models that can reason about your specific data.**

Models like GPT-4o, Claude, and the open-source Llama family can receive a business question in plain English, process structured context about your business, and produce a reasoned answer with supporting evidence. This is qualitatively different from LSTM: instead of predicting a number from a sequence, the model reasons about meaning.

The challenge is that these models are trained on the internet, not on your business. They know nothing about your sales, your suppliers, or your specific situation. This is where RAG comes in.

**Retrieval-Augmented Generation (RAG).**

[RAG was introduced by Patrick Lewis et al. at Facebook AI Research in 2020](https://arxiv.org/abs/2005.11401). The core idea: before the language model answers a question, retrieve relevant documents from a private knowledge base and include them as context. The model reasons over your documents, not just its training data.

For a non-technical reader: imagine hiring a consultant who is brilliant but just arrived today. Before answering anything, they go to your filing cabinet, find the relevant records, read them, and then form their answer based on what they found. RAG is that process, automated.

For a technical reader: the retrieval step uses vector embeddings, mathematical representations of text that capture semantic meaning rather than literal keywords. Similar concepts produce similar vectors. This means a query about "slow months" will retrieve documents about "seasonal downturns" even if those exact words never appear together. The embeddings are stored in [pgvector](https://github.com/pgvector/pgvector), a PostgreSQL extension that adds approximate nearest-neighbor search over vector columns.

```sql
-- pgvector nearest-neighbor retrieval
SELECT id, content, label
FROM document_chunks
ORDER BY embedding <=> query_vector
LIMIT 10;
```

The `<=>` operator is the cosine distance function added by pgvector. It finds the chunks whose meaning is closest to the query vector, in milliseconds, even over large collections.

![RAG architecture: from business data to cited answer](./images/biased-rag-architecture.png)

*The RAG pipeline. Your business data is chunked, embedded, and stored. At query time, the question is embedded and matched against stored chunks. The retrieved evidence feeds the language model, which produces an answer with citations.*

## B.I.A.S.E.D. today: architecture and data flow

The current release is v1.0.0-showcase. The repository is a [pnpm monorepo](https://pnpm.io/workspaces) with four main packages: a Next.js PWA frontend, a FastAPI backend, a shared contracts package, reusable UI primitives, infrastructure configuration, and sanitized demo fixtures.

![B.I.A.S.E.D. monorepo structure: six packages across apps, shared packages, and infrastructure](./images/biased-monorepo.png)

[Zod](https://zod.dev/): schema validation for shared contracts. These contracts live in the shared package so the TypeScript frontend and Python backend agree on every request and response shape without duplication. Change a contract and both sides fail their type checks immediately.

The high-level data flow splits into two parallel tracks that converge at the orchestrator. The first track handles data ingestion: the owner imports business records, the API normalises them, and Postgres stores them with pgvector indexing the semantic embeddings. The second track handles questions: the user asks something in plain English, it hits the investigation API, and reaches the orchestrator. The orchestrator runs the SQL analyst and RAG retriever in sequence, then passes their combined findings to the response writer, which assembles the final cited answer.

![B.I.A.S.E.D. end-to-end data flow: ingestion and investigation tracks converging at the orchestrator](./images/biased-data-flow.png)

## The investigation pipeline in detail

This is the technical core of B.I.A.S.E.D. Source: `apps/api/src/api/services/agent_orchestration.py`.

When a user submits a question to `POST /api/investigations`, the backend runs the following sequence:

**Step 1: Guardrails.**

The question passes through `guard_question`, which blocks SQL injection, control-like prompts, and attempts to access data outside the user's workspace. This is not optional: an AI system that executes arbitrary instructions against a business database is a security risk, not a feature.

**Step 2: Task classification.**

The orchestrator infers the task class: `summarize`, `investigate`, or `recommend`. This determines which tools will be invoked and how the response writer will frame the output.

**Step 3: Provider selection.**

The runtime mode is read from the workspace's model profile: `local-open` (Ollama on the same machine), `byo-cloud` (user-provided API key for OpenAI, Anthropic, or Groq), or `hybrid` (task-sensitive routing between local and cloud). Provider metadata (model name, mode, estimated cost per query) is returned in every response so the user can see exactly what ran.

**Step 4: Orchestration route.**

The orchestrator executes a four-step route:

```
router -> sql_analyst -> rag_retriever -> response_writer
```

The implementation uses [LangGraph](https://langchain-ai.github.io/langgraph/) when available, with a linear fallback for environments where it cannot be loaded. LangGraph models the orchestration as a directed graph of nodes: each node is a tool call, and the graph controls the sequence, the data passed between steps, and error handling at each stage.

The SQL analyst runs safe, parameterized queries against the operational tables (sales, purchases, expenses) to compute metrics: revenue by period, top products, expense trends. It runs only a predefined set of read-only analytical queries.

The RAG retriever converts the question to an embedding, runs `<=>` nearest-neighbor search over `document_chunks`, and returns the top matching chunks with their source labels.

**Step 5: Response assembly.**

The response writer receives the SQL findings and RAG citations and calls the language model to synthesize a final answer. The model does not see the raw database; it receives structured context prepared by the preceding tools.

**Step 6: Structured output.**

The investigation response has a fixed schema:

```typescript
// From packages/contracts/src/index.ts
{
  summary: string,
  confidence: number,          // 0 to 1
  evidence: Evidence[],        // citations with label, detail, source
  risks: string[],
  recommendations: string[],
  provider: string,
  mode: "local-open" | "byo-cloud" | "hybrid",
  latency_ms: number,
  estimated_cost_usd: number,
  orchestration: {
    route: string[],
    toolCalls: ToolCallMeta[]  // name, status, runtime_ms, detail
  }
}
```

The `orchestration.route` and `toolCalls` fields are returned to the client, not hidden. This is deliberate: a business owner making a decision deserves to know what the system actually did to form its answer, not just what the answer is.

A note on the current showcase: the embedding strategy in this release uses a deterministic hashed approach with 24-dimensional vectors for reproducible demo behavior. This prioritizes predictability over production-grade semantic quality. A deployment pointing at a real embedding model (text-embedding-3-small, nomic-embed-text via Ollama, etc.) would replace this with full semantic retrieval.

## Importing and storing business data

Before the AI can investigate anything, the data has to get in. B.I.A.S.E.D. uses a two-phase import pipeline to handle real-world messiness without silently corrupting records. Source: `apps/api/src/api/services/demo_data.py`.

**Phase 1: Preview.**

`POST /api/import-jobs` accepts CSV or Excel files via [Polars](https://pola.rs/) (for CSV) and [OpenPyXL](https://openpyxl.readthedocs.io/) (for Excel). The API infers column mappings, flags missing required fields, and returns a preview with warnings. The user sees exactly what will be imported before anything is committed.

Supported import types: `sales`, `purchases`, `products`, `expenses`, `recurring_obligations`.

**Phase 2: Confirm.**

`POST /api/import-jobs/{id}/confirm` applies the normalized rows into the target domain tables. If anything fails at this stage, no partial data is written. The confirmation is transactional.

After confirmation, imported documents are chunked (fixed 280-character segments) and their embeddings are written to `document_chunks` with a `vector(24)` column. This is what the RAG retriever searches.

## Forecasting and scenario planning

Not all business questions are open-ended. B.I.A.S.E.D. also includes deterministic, explainable analytical tools that do not depend on a language model at all.

**Forecasting** (`POST /api/forecasts/run`) uses a moving-average baseline over recent transactional data. Supported metrics: `sales`, `purchases`, `recurring`, `cash`. The response includes the computed assumptions and any warnings (for example, "insufficient data for reliable 90-day forecast") alongside the numbers. This is intentionally transparent: a single number without its assumptions is not a useful forecast.

**Scenario planning** (`POST /api/scenarios/run`) models four implemented scenarios:

- `supplier_price_increase`: impact on purchase costs and margins
- `underperforming_product_line`: revenue delta from removing or repricing a product
- `delayed_reorder`: cash flow impact of a stockout event
- `rent_electricity_increase`: operating cost impact on net position

Each scenario returns a structured diff: baseline values, projected values, and impact deltas, with recommendations. The calculations are deterministic and auditable. No black-box AI involved.

**Scheduler** (`POST /api/scheduler/run`) scans recurring obligations and transaction patterns to produce a brief with upcoming obligations, detected anomalies, and reminders. This runs on a schedule to keep the action center populated.

## MCP: connecting to external tools

[Model Context Protocol (MCP)](https://modelcontextprotocol.io/) is an open standard introduced by Anthropic in 2024 that defines how AI systems can expose tools to external clients in a structured, interoperable way. B.I.A.S.E.D. implements a JSON-RPC MCP endpoint at `POST /mcp`. Source: `apps/api/src/api/services/mcp_rpc.py`.

Exposed JSON-RPC methods:

```
initialize           Handshake and capability negotiation
tools/list           Returns the available tool schemas
tools/call           Executes a named tool with arguments
```

Exposed tools:

```
investigate          Submit a business question for AI investigation
run_forecast         Run a metric forecast
run_scenario         Run a named scenario plan
run_scheduler        Trigger the scheduler run
read_import_ledger   Inspect the import job history
```

This means any MCP-compatible client (other AI agents, automation tools, or custom scripts) can invoke B.I.A.S.E.D.'s workflows programmatically, not just through the web UI. A user who wants to run a weekly investigation from a cron job or trigger a forecast from another application can do so through the MCP interface without touching the web frontend.

## Data model, RBAC, and the workspace model

Every piece of data in B.I.A.S.E.D. belongs to a workspace. A workspace is the unit of isolation: different businesses are different workspaces, and data never crosses workspace boundaries.

The core operational tables:

```
workspaces               workspace members
products                 model_provider_settings
sales_transactions       business_documents
purchase_transactions    document_chunks (pgvector)
expense_entries          import_jobs / import_rows
recurring_obligations    action_center_items
                         scheduler_runs
```

Schema bootstrap lives in `apps/api/src/api/services/demo_data.py`. The frontend uses a [Drizzle ORM](https://orm.drizzle.team/) mirror in `apps/web/lib/schema.ts` so TypeScript types stay in sync with the database schema.

Access control uses three roles enforced through RBAC helpers in `apps/web/lib/rbac.ts`:

- `owner`: full access, settings, imports, AI features, all data
- `manager`: operational access, transactions, imports, AI features
- `accountant`: read and expense access, view data, add expenses

[Better Auth](https://www.better-auth.com/) handles session management, email verification, and the auth plumbing in `apps/web/lib/auth.ts`. It is provider-agnostic and does not require a third-party auth service.

## Running it: two paths

**Self-hosted (local-first, data stays on your machine).**

```bash
git clone https://github.com/theSelfSa/biased
cd biased
docker compose -f infra/docker-compose.yml up
```

Docker Compose starts four services:

```
postgres (pgvector)    port 5433
ollama                 port 11434
api (FastAPI)          port 8000
web (Next.js)          port 3000
```

With Ollama running locally, no business data ever leaves the machine. The language model runs on the same hardware as the database. For a small business owner handling sensitive financial records, this matters.

**Hosted path.**

For users who want managed infrastructure:

- Web: [Vercel](https://vercel.com/)
- API: [Render](https://render.com/)
- Database: [Supabase](https://supabase.com/) with pgvector extension enabled

In this path, the `byo-cloud` mode routes model calls to a cloud provider using the user's own API key. The host never holds the API key beyond the session.

## What it does not do (honest limitations)

The current release is labeled v1.0.0-showcase for a reason.

The embedding strategy uses deterministic hashed vectors for reproducibility in the demo environment. Real semantic quality requires a proper embedding model. Ollama ships several options (nomic-embed-text, mxbai-embed-large) and OpenAI's text-embedding-3-small is cost-effective for cloud deployments. The architecture supports swapping this in; the showcase build does not do it automatically.

Enterprise concerns (SLAs, dedicated support, hardened multi-region infrastructure, compliance certifications) are out of scope for an open-source single-developer showcase release. Organizations with those requirements need a managed vendor.

The "local-first + open-source" design is a deliberate trade-off: maximum privacy and zero ongoing cost, with the trade-off being that the user manages their own infrastructure and accepts the limitations of whatever local hardware they have.
